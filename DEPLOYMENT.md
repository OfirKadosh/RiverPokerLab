# Free trial deployment preparation

The complete application is stored in the private `OfirKadosh/RiverPokerLab` repository. The initial personal trial is now live at https://river-poker-lab.onrender.com/ and the user confirmed the core flow. This guide retains the setup instructions. The stabilization branch described in [BETA_STABILIZATION.md](BETA_STABILIZATION.md) has not been merged or deployed.

## Topology and current access

One Node/Express web service serves both the built React client and `/api`. The browser uses relative `/api` requests, so secure session cookies work on one HTTPS origin. Existing hash navigation remains unchanged. MongoDB Atlas stores users, sessions, rate-limit counters and explicitly saved spots; the web service does not need a persistent disk.

Registration stays open. A new account cannot use calculators or history until activated. In the initial manual mode the administrator hands the registrant a code from private server logs. This introduces a manual activation step for each new account, without an invitation list or automated email/SMS. Once activated, every account has the full beta functionality and its own saved history. Payments and usage entitlements are not implemented.

## Prepared Render settings

`render.yaml` defines a single Free Node service, using the existing Atlas database. Render's application installation must separately have access to the private GitHub repository; connecting GitHub to ChatGPT does not grant Render access.

| Setting | Value |
| --- | --- |
| Repository / branch | `OfirKadosh/RiverPokerLab` / `main` |
| Runtime | Node 22 |
| Root directory | Repository root; leave blank |
| Build command | `npm --prefix backend ci --omit=dev && npm --prefix frontend ci --include=dev && npm run build` |
| Start command | `npm start` |
| Initial compute plan | Free |
| Health check | `/healthz` |
| Automatic deploys | Off; deploy explicitly after reviewing changes |

The blueprint uses `sync: false` for `MONGO_URI` and `EMAIL_PROVIDER`. During initial setup, enter your actual Atlas URI privately and enter `manual` for `EMAIL_PROVIDER`. `AUTH_SECRET` is generated by Render. Never paste these secrets in chat, commit them, or use frontend variables for them. If creating the service manually instead of applying the blueprint, use `backend/.env.production.example` as a settings checklist and generate a fresh random secret yourself.

Render supplies `PORT` and `RENDER_EXTERNAL_URL`. The server listens on `0.0.0.0` and uses that URL as the exact allowed origin when `APP_ORIGINS` is unset. Do not copy the local `.env` wholesale: its localhost origins and development delivery are unsuitable. For a custom domain later, set `APP_ORIGINS` to the actual HTTPS origins, comma-separated without trailing slashes or paths.

`TRUST_PROXY_HOPS=1` is configured for one trusted hosting proxy in front of the process. If the hosting topology changes, recheck this value. Production account/API operations require HTTPS and keep Secure, HttpOnly, SameSite=Lax cookies and CSRF/origin checks. The public `/healthz` returns only `ok` or `unavailable` and reports 503 if MongoDB disconnects. Startup waits for MongoDB and required indexes before accepting traffic.

## Manual activation from private logs

The hosted manual provider is separate from development delivery:

```dotenv
NODE_ENV=production
AUTH_ALLOW_DEV_DELIVERY=false
AUTH_ALLOW_MANUAL_DELIVERY=true
EMAIL_PROVIDER=manual
SMS_PROVIDER=disabled
SERVE_FRONTEND=true
```

1. A tester registers with email, username, international phone and password.
2. The page says to ask the administrator for an activation code; it does not claim that an email was sent.
3. In the service's private runtime logs, find the JSON event `manual_account_activation` for the requested username and user ID. It contains the eight-digit code and its ten-minute validity. Codes never appear in an API response, client console or database plaintext.
4. Confirm which tester you are approving, then share that account's code with them yourself. Treat log access as access to pending activation codes; do not share full runtime logs with testers.
5. The tester enters the code and signs in. Pending sessions last twenty minutes. Expired codes can be replaced through Resend verification code, subject to the existing sixty-second cooldown and rate limits.

Manual activation sets `accountApprovedAt`; it does **not** set `emailVerifiedAt` or `phoneVerifiedAt`. The Account page explains the administrator approval and displays both contact statuses accurately. The delivery method is saved with each challenge, so switching providers does not convert an old manual challenge into proof of email ownership. Existing genuine email/SMS approvals keep working. Contact details must not be used for automated account recovery unless actually verified. Password recovery is not implemented.

Eight-digit randomness, hashed storage, expiration, five attempts, one-use atomic consumption, persistent throttling and private history ownership remain enforced. The default remains disabled: logging activation codes on a hosted server requires both the `manual` provider and the explicit opt-in flag. Development delivery is still rejected in Production.

## Actual deployment checklist (not performed yet)

1. Authorize Render for this private repository and create the service using the prepared settings. Applying the Blueprint or clicking Create Web Service starts a real deployment; uploading these files to GitHub alone does not.
2. Enter the Atlas URI and `manual` provider in Render. Use a database user restricted to the application's intended database. Retain the same database and AUTH_SECRET across service upgrades/redeploys.
3. In Atlas Network Access, permit the outbound addresses shown by your Render service. Do not assume the developer laptop's IP allowlist also covers the host. Do not put database credentials in a URL sent through chat.
4. Check build/start logs and the actual service URL's `/healthz`. The URL/name is not reserved by these files and may differ from the suggested name.
5. Complete registration, manual activation, login and Remember me on the live HTTPS URL. Save a spot, sign out, sign back in, and check history. Register a second account with distinct contact details and confirm its empty history. Check on an actual phone.
6. Redeploy/restart and confirm that login/history persist through Atlas. Verify logout revokes access. Check resource use during a representative Hold'em/Omaha and weighted-range calculation.

These live checks are required before calling the hosted beta validated. Local tests do not establish live Atlas connectivity, Render network routing or sustained load performance.

## Upgrading later without rebuilding the app

Keep the same service, URL, repository and Atlas database. Upgrade the compute plan in Render when inviting testers; payment and the plan change do not require changing application code. A Blueprint re-sync applies its declared `plan: free`, so leave automatic Blueprint sync disabled and review any future sync rather than unintentionally applying the initial free plan again. Code auto-deploys are also off initially.

For automatic email, verify a domain in Resend and change runtime settings to `EMAIL_PROVIDER=resend`, `RESEND_API_KEY=...`, `EMAIL_FROM=...`, and `AUTH_ALLOW_MANUAL_DELIVERY=false`. Keep `SMS_PROVIDER=disabled` unless separately configured. Restart/redeploy to apply environment changes. No source change is needed. Existing manually activated users keep access; their contact status does not silently become verified. New email challenges prove the contact normally. Future billing/paid access is a separate feature and is not enabled by paying the hosting provider.

The free service can sleep after inactivity and has limited CPU/RAM. Memory-heavy scrypt derivations are serialized within this single Node process and the waiting queue is capped; overload returns a retryable 503 without weakening password hashing. In the stabilization branch, heavy calculations run on one bounded worker thread while account/history operations stay on the main thread; see BETA_STABILIZATION.md for queue and timeout limits. Start with personal testing, measure representative calculations, and reassess concurrency before distributing broadly. Upgrading improves resources but is not a guarantee of performance for arbitrary workloads.
